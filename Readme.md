## Теоретическая база

### Мультимодальный RAG (Retrieval-Augmented Generation)

Классический RAG опирается исключительно на текстовый поиск, что делает невозможным анализ визуальной информации (графиков, диаграмм, сложных таблиц), часто встречающейся в PDF-документах. В данной работе реализован подход **Multimodal RAG**, который объединяет семантический поиск по текстовым эмбеддингам с мощностью мультимодальных языковых моделей (Vision-Language Models, VLM). Это позволяет передавать нейросети не только найденный релевантный текстовый фрагмент, но и полное изображение страницы-источника.

### Предобработка PDF-документов

Для подготовки данных к векторизации и генерации ответов используется библиотека `PyMuPDF` (`fitz`):
1. **Извлечение текста**: Из каждой страницы извлекается сырой текст для последующего семантического поиска.
2. **Рендеринг изображений**: Каждая страница параллельно рендерится в PNG-изображение (с масштабом x2 для сохранения читаемости мелкого текста и графиков). Изображения сохраняются в базе данных в бинарном формате (BYTEA).

### Векторизация и экспериментальное сравнение энкодеров

Для обеспечения качественного поиска длинный текст страниц разбивается на пересекающиеся фрагменты (чанки) размером 500 символов с нахлестом (overlap) в 50 символов.
В системе реализована поддержка трех различных моделей-энкодеров (Encoders) из библиотеки `SentenceTransformers`:
* `bge-m3`
* `all-MiniLM-L6-v2`
* `multilingual-e5-small`

Выбор энкодера доступен через API во время загрузки документа. Веса моделей предварительно скачиваются (запекаются) на этапе сборки Docker-образа, что обеспечивает мгновенный запуск системы без зависимости от скорости скачивания в runtime.

### База данных и векторный поиск (pgvector)

Для хранения метаданных документов, изображений страниц и текстовых эмбеддингов используется реляционная СУБД **PostgreSQL** с установленным расширением **pgvector**.
Векторная колонка настроена без жестко заданного размера, что позволяет гибко хранить векторы разной размерности (например, 1024 для `bge-m3` и 384 для `MiniLM`).
Поиск наиболее релевантного фрагмента текста осуществляется средствами СУБД с использованием оператора косинусного расстояния (`cosine_distance`).

### Генерация ответов (VLM)

В качестве мультимодального генератора используется модель **Google Gemini 2.5 Flash** (через API). 
Модель получает комплексный промпт, состоящий из:
1. Системной инструкции (ограничивающей галлюцинации и заставляющей модель опираться строго на контекст или честно отказываться отвечать при отсутствии данных).
2. Текста наиболее релевантной страницы, найденной через векторный поиск.
3. Изображения этой страницы (передается в формате Base64).
4. Вопроса пользователя.

### Архитектура приложения

* **Backend**: Построен на фреймворке `FastAPI`. Обработка PDF вынесена в фоновые задачи (`BackgroundTasks`). При генерации ответа собираются и возвращаются ключевые метрики: время поиска в БД, время работы VLM и косинусное расстояние.
* **Frontend**: Разработан на `React` + `Vite` с использованием `Tailwind CSS`. 
* **Автоматизированное E2E тестирование**: Разработан скрипт бенчмаркинга (`run_tests.py`), который автоматически загружает статьи, прогоняет через них набор вопросов (включая вопросы "с подвохом", ответы на которые отсутствуют в тексте) для каждого из трех энкодеров, собирает метрики и строит графики сравнения.
* **Контейнеризация**: Вся система упакована в `Docker Compose`. Модели ML предварительно загружаются в образ `Backend`.

## Анализ результатов выполнения программы

В ходе выполнения лабораторной работы была успешно разработана, протестирована и проанализирована система визуального вопросно-ответного поиска по PDF-документам.

### Бенчмаркинг и E2E Тестирование
Для объективного сравнения энкодеров был разработан специализированный E2E-скрипт тестирования. Скрипт проверил 3 модели на 5 различных статьях (25 вопросов на каждый энкодер).
* **Скрипт тестирования:** [`backend/Test/run_tests.py`](backend/Test/run_tests.py)
* **Результаты тестов (Отчет Markdown):** [`backend/Test/test_report.md`](backend/Test/test_report.md)

Детальный анализ отчета выявил следующие особенности:

1. **Точность векторного поиска (Accuracy) и проблема языкового барьера**
   Эксперимент наглядно показал, что англоязычная легковесная модель `all-MiniLM-L6-v2` практически полностью провалила тест на русскоязычных текстах, выдавая нерелевантные страницы в абсолютном большинстве случаев. В то же время мультиязычные модели (`bge-m3` и `multilingual-e5-small`) справились с задачей на высоком уровне, стабильно находя нужный контекст даже в сложных исторических и технических документах.

2. **Скорость работы (Retrieval Time) и косинусное расстояние**
   * Тяжелая модель `bge-m3` показала среднее время поиска в БД на уровне **0.12 - 0.15 сек.**, при этом косинусное расстояние варьировалось в пределах `0.25 - 0.45`.
   * Модель `multilingual-e5-small` оказалась золотой серединой: она обеспечила высокую скорость (в среднем **0.02 - 0.03 сек.**, сравнимо с `MiniLM`) при отличной точности. При этом косинусное расстояние у `e5-small` было рекордно низким (`0.05 - 0.15`), что говорит о высокой математической «уверенности» модели в найденных результатах.

3. **Обработка Out-of-Domain запросов (True Negatives)**
   Добавление вопросов, не связанных с текстом статьи (например, вопрос о кормлении британской кошки или дате релиза Python в документе по архитектуре C#), позволило проверить иммунитет RAG-системы к галлюцинациям. Векторная БД возвращала формально ближайший фрагмент, но строгий системный промпт заставлял Gemini анализировать контекст: модель успешно определяла отсутствие информации и честно отвечала отказом («Не могу найти информацию»), что подтверждает безопасность разработанного пайплайна.

4. **Скорость развертывания и оптимизация среды**
   Включение загрузки весов моделей (`SentenceTransformer`) непосредственно в `Dockerfile` (на этапе сборки образа) решило проблему "холодного старта" и сделало развертывание контейнера моментальным, отвязав приложение от необходимости каждый раз скачивать тяжелые веса по сети.

### Общий вывод

Создан полноценный прототип Multimodal RAG-системы, готовый к эксплуатации, с мощным аналитическим инструментарием для бенчмаркинга моделей. Сквозное тестирование доказало, что выбор правильного энкодера критически влияет на конечный результат: для русскоязычных задач оптимальным решением с точки зрения баланса «скорость/качество» выступает `multilingual-e5-small`.
Система продемонстрировала высокую устойчивость как при поиске информации в сложных визуальных данных, так и при обработке ложных запросов, успешно избегая галлюцинаций.
