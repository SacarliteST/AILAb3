## Теоретическая база

### Мультимодальный RAG (Retrieval-Augmented Generation)

Классический RAG опирается исключительно на текстовый поиск, что делает невозможным анализ визуальной информации (графиков, диаграмм, сложных таблиц), часто встречающейся в PDF-документах. В данной работе реализован подход **Multimodal RAG**, который объединяет семантический поиск по текстовым эмбеддингам с мощностью мультимодальных языковых моделей (Vision-Language Models, VLM). Это позволяет передавать нейросети не только найденный релевантный текстовый фрагмент, но и полное изображение страницы-источника.

### Предобработка PDF-документов

Для подготовки данных к векторизации и генерации ответов используется библиотека `PyMuPDF` (`fitz`):
1. **Извлечение текста**: Из каждой страницы извлекается сырой текст для последующего семантического поиска.
2. **Рендеринг изображений**: Каждая страница параллельно рендерится в PNG-изображение (с масштабом x2 для сохранения читаемости мелкого текста и графиков). Изображения сохраняются в базе данных в бинарном формате (BYTEA).

### Векторизация и фрагментация текста

Для обеспечения качественного поиска длинный текст страниц разбивается на пересекающиеся фрагменты (чанки) размером 500 символов с нахлестом (overlap) в 50 символов. 
В качестве модели-энкодера (Encoder) используется `all-MiniLM-L6-v2` из библиотеки `SentenceTransformers`. Она трансформирует текстовые чанки в плотные векторы (эмбеддинги) размерностью 384. Данная модель выбрана благодаря её высокой скорости работы, малым требованиям к оперативной памяти и отличному качеству для задач семантического поиска.

### База данных и векторный поиск (pgvector)

Для хранения метаданных документов, изображений страниц и текстовых эмбеддингов используется реляционная СУБД **PostgreSQL** с установленным расширением **pgvector**.
Поиск наиболее релевантного фрагмента текста осуществляется средствами СУБД с использованием оператора косинусного расстояния (`cosine_distance`). Такой подход позволяет эффективно находить нужную страницу среди сотен документов без выгрузки векторов в оперативную память приложения.

### Генерация ответов (VLM)

В качестве мультимодального генератора используется модель **Google Gemini 2.5 Flash** (через API). 
Модель получает комплексный промпт, состоящий из:
1. Системной инструкции (ограничивающей галлюцинации и заставляющей модель опираться строго на контекст).
2. Текста наиболее релевантной страницы, найденной через векторный поиск.
3. Изображения этой страницы (передается в формате Base64).
4. Вопроса пользователя.

### Архитектура приложения

* **Backend**: Построен на фреймворке `FastAPI`. Обработка тяжелых PDF-документов вынесена в фоновые задачи (`BackgroundTasks`), чтобы не блокировать основной поток приложения. Внедрен пуллинг статусов.
* **Frontend**: Разработан на `React` + `Vite` с использованием `Tailwind CSS`. Реализован SPA-интерфейс с боковой панелью управления документами, динамическим прогресс-баром обработки файлов и интерфейсом чата, отображающим как текстовый ответ ИИ, так и картинку страницы-источника (Visual Grounding).
* **Контейнеризация**: Вся система (СУБД, Backend, Frontend) упакована в `Docker Compose` для обеспечения воспроизводимости среды и быстрого развертывания.

## Анализ результатов выполнения программы

В ходе выполнения лабораторной работы была успешно разработана и протестирована система визуального вопросно-ответного поиска по PDF-документам.

Детальный анализ процесса выявил следующие особенности:

1. **Асинхронная обработка и стабильность системы**
   Перенос задач парсинга, рендеринга изображений и генерации эмбеддингов в фоновый поток (Background Tasks) FastAPI полностью решил проблему зависания веб-интерфейса при загрузке многостраничных документов. Система очередей успешно блокирует одновременную обработку более 3 документов.

2. **Эффективность векторного поиска**
   Использование легковесной модели `all-MiniLM-L6-v2` в связке с `pgvector` показало высокую точность извлечения контекста. Замена изначально планировавшейся тяжелой модели `bge-m3` позволила существенно снизить потребление ОЗУ (с 8+ ГБ до < 1 ГБ) без видимой потери качества поиска на англо- и русскоязычных текстах. Настройка чанкования с перекрытием (overlap = 50) помогла избежать потери смысла на стыке абзацев.

3. **Качество ответов VLM (Gemini 2.5 Flash)**
   * **Положительные аспекты**: Модель превосходно справляется с извлечением информации из графиков, таблиц и схем, которые теряются при классическом парсинге текста. Предоставление странице в виде изображения позволяет VLM "понимать" визуальную иерархию документа.
   * **Ограничения (Галлюцинации)**: При отсутствии информации на найденной странице модель иногда склонна додумывать факты, несмотря на строгий системный промпт. Также качество ответа напрямую зависит от работы этапа поиска (Retriever): если векторный поиск выдаст страницу без ответа, VLM не сможет ответить на вопрос, даже если нужная информация есть на соседней странице документа.

### Общий вывод

Создан полноценный прототип Multimodal RAG-системы, готовый к эксплуатации. Интеграция базы данных `pgvector`, современных легковесных LLM для эмбеддингов и API Gemini доказала свою эффективность. 
Основной потенциал для дальнейшего развития (улучшения) кроется в совершенствовании этапа Retrieval: например, внедрение механизма поиска по соседним страницам (Context Window Expansion) или использование гибридного поиска (BM25 + Dense Vectors) для более точного нахождения терминов.
